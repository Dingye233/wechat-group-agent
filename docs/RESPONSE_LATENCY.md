# 读取与回复速度

群伴的回复延迟由四段组成。优化前，普通群聊从微信落库到消息发出常见 **5–8 秒**（mem0 冷启动时更久）；优化后目标 **3–5 秒**，短句闲聊可以到 3 秒左右。

## 1. 链路与耗时

```text
微信写库
  → 监听线程发现新消息（轮询间隔 0.5s）
  → 调度队列投递（0–0.1s）
  → 运行时入库 / 触发判断（<20ms）
  → 同人合并窗口（0.15–0.4s）
  → 上下文 + 记忆 + 工具 + 意图规划
  → 回复延迟（0.5–1.0s，与合并窗口不重复计算）
  → 模型生成（0.6–1.5s）
  → wechatauto 发送 + 数据库确认（0.5–2s）
```

`Agent 动态` 里的回复记录现在带有分阶段耗时：

```text
｜阶段：前置 620ms / 生成 780ms / 发送 930ms / 端到端 3100ms
```

- **前置**：从进入 Agent 到规划完成（含合并窗口、上下文、记忆、意图规划）。
- **生成**：回复模型调用。
- **发送**：UI 发送 + 微信数据库落库确认。
- **端到端**：从消息入库到回复发送完成。

### 实测（数据库副本 + 假模型/假发送）

把一条真实格式的“你好”插入测试群副本，用假模型和假发送跑完整 `_handle`：

```text
阶段：前置 381ms / 生成 263ms / 发送 79ms / 端到端 730ms
模型调用：1 次（短闲聊跳过意图规划）
```

固定等待 + 上下文 + 入库的同步开销已经压到 1 秒以内；真实模型通常再增加 0.7–1.2 秒，真实微信发送增加 0.5–2 秒。mem0 冷启动时每条消息原本要多等 2–3 秒，现在直接走 SQLite 记忆，不再阻塞。

## 2. 本次优化

| 位置 | 之前 | 现在 | 收益 |
| --- | --- | --- | --- |
| 数据库监听 | 固定 1.0s 轮询 | 默认 0.5s，可在设置里调 | 减少 0–0.5s |
| 待投递队列 | 每个群再等 1s 才 emit | 发现即投递 | 减少 0–1s |
| mem0 检索 | 与记忆提取共用一把锁，冷启动 2.8s | 读写锁分离 + 启动预热 + 未就绪直接跳过 | 减少 0–2.8s |
| 意图规划 | 每条消息都调用一次模型 | 50 字以内、无任务词的闲聊跳过规划 | 减少 0.8–1.1s |
| 合并窗口 + 回复延迟 | 两段各等一次 | 合并窗口从回复延迟里扣除 | 减少 0.15–0.4s |
| 发送确认 | 每 0.4s 查一次，最多 6s | 前 0.8s 每 0.2s 查一次 | 平均减少 0.2–0.4s |

## 3. 可调参数

| 设置项 | 默认 | 说明 |
| --- | --- | --- |
| `read_poll_interval_seconds` | 0.5 | 数据库轮询间隔；群多/CPU 紧张时可调回 1.0 |
| `reply_delay_seconds` | 0.8 | 回复前的基础停顿（人味） |
| `reply_delay_random_seconds` | 1.5 | 随机追加停顿 |
| `memory_search_timeout_seconds` | 1.5 | mem0 语义记忆预算；超时直接用 SQLite 记忆 |
| `fast_chat_planner` | true | 短闲聊跳过意图规划模型 |
| `memory_engine` | auto | 设为 `sqlite` 可完全关掉 mem0 |

> 当前这台机器已把 `read_poll_interval_seconds` 调到 `0.5`、`reply_delay_seconds` 调到 `0.4`、`reply_delay_random_seconds` 调到 `0.9`，比代码默认值更快。想恢复更自然的节奏，在设置页改回 `0.8 / 1.5` 即可。

> 合并窗口（0.15–0.4s）已经计入回复延迟，不会再额外叠加。把 `reply_delay_seconds` 调到 0.3、`reply_delay_random_seconds` 调到 0.7，可以再快 0.3–0.5 秒，但会更像机器人。

## 4. 什么时候还会慢

- **消息带图片/文件**：监听线程会先解密媒体再投递，图片多时同一轮的文字消息会被拖慢。
- **任务型消息**：需要工具或转交 OpenCode，先回一句过渡语，完整结果在后台任务里，不计入这条回复的延迟。
- **微信界面发送**：窗口被最小化、锁屏或 UIA 卡住时，发送确认会退化为 3s + 4s 的兜底检查。
- **OpenCode 首次启动**：第一次群任务转交需要启动 sidecar，约 2–5 秒；之后复用。
- **mem0 冷启动**：服务启动后的前几条消息可能只用 SQLite 记忆，预热完成后自动恢复语义记忆。
